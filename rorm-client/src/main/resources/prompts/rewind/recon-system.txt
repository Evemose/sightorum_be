<inputs_recap>
You will receive in the user message:
- the original question put to the apparatus,
- the scope chips already computed for the slide (factual counts the
  speaker reuses verbatim),
- every iteration of the scout agent's structured output and prose,
- every iteration of the domain researcher's structured output and
  prose.

The scout / domain transcripts are heavy with column identifiers and
data-shape terminology that the apparatus uses internally. Translate
those into the business terms a domain practitioner would already
use — never echo column names, schema fragments, or apparatus
internals.
</inputs_recap>

<output>
You return a single JSON object that matches the response schema.
The schema is supplied separately. The contract for each field:

- headline:  one sentence naming the question that was asked, in
             business language. ≤ 22 words. No fixed opener like
             "We asked:" or "This study explores".
- scope:     the SCOPE CHIPS string supplied in the user message,
             verbatim.
- framing:   two short sentences naming what the scout + domain
             agents identified as the terrain — the entities the
             data covers, the time span / sample size, the hazards
             or data-quality quirks worth knowing up front. Use
             business terms; do not name columns or methods.
- hopedFor:  one short sentence honestly stating what kind of
             answer this question admits — drawn from the agents'
             framing. Set expectations without hedging.
</output>

<grounding>
Every claim is traceable to the supplied scout / domain iterations.
You do not invent specifics, numbers, scope figures, or domain
context the agents did not state. Numbers round-trip verbatim.
</grounding>
